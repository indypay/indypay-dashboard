1. System Overview & Architecture

RupeeFlow's Payment Links feature lets merchants generate shareable, time-limited payment links that customers can open to complete a payment through QR, UPI, Card, or Net Banking.

Merchant (Dashboard) Path

Authenticated merchant creates a link, views analytics, sends reminders.

Routes: /dashboard/payment-links, /dashboard/payment-button

Customer (Checkout) Path

Unauthenticated customer opens link URL, selects payment method, completes payment.

Route: /payment-link/[linkId]

Base URL Convention

https://api.rupeeflow.com/v1

URL Routing

Frontend URL Description Auth Required
/dashboard/payment-linksMerchant: list, create, manage linksYes (JWT)
/dashboard/payment-buttonMerchant: create links + hero/analyticsYes (JWT)
/payment-link/[linkId]Customer: checkout pageNo
/checkout/[id]Legacy checkout (being phased out)No

Technology Stack (Frontend — context)

Next.js 14 App Router TypeScript React Query Axios Ant Design AES-256-GCM Encryption

3. Authentication & Authorization

ℹ️
Dual Authentication Model Merchant APIs require JWT Bearer token. Customer checkout APIs are public (unauthenticated) — the linkId acts as an access token for the specific payment session.

Merchant API Auth (Dashboard)

Authorization: Bearer <JWT_ACCESS_TOKEN>
Content-Type: application/json

Customer / Checkout API Auth

No Authorization header required. The linkId in the URL path is the sole identifier.

⚠️
Rate Limiting Required Customer-facing endpoints must be rate-limited per IP to prevent brute-force link enumeration. Recommended: 30 requests / minute per IP for GET, 5 requests / minute per IP for POST (payment initiation).

Existing Auth Used by Frontend

The frontend also sends Basic Auth on the legacy initiate-payin-payment endpoint.

Authorization: Basic <base64(username:password)>

New endpoints should migrate to JWT Bearer only.

4. Merchant APIs — Payment Link Management

4.1 Create Payment Link

POST /payment-links Auth: JWT

Creates a new payment link and optionally sends notification to the customer.

Request Body

{
  "amount": 1500.00,               // Required. Amount in INR (positive decimal)
  "name": "Rahul Sharma",         // Optional. Customer name
  "email": "rahul@example.com",   // Required. Customer email
  "mobile": "9876543210",        // Required. 10-digit mobile number
  "expiresInMinutes": 1440,      // Required. Expiry from now in minutes (e.g. 1440 = 24h)
  "notifyEmail": true,           // Optional. Send email to customer
  "notifyNumber": true,          // Optional. Send SMS to customer
  "description": "Invoice #1042",  // Optional. Order note (max 500 chars)
  "allowPartialPayment": false,   // Optional. Allow paying less than amount
  "minimumAmount": 500.00,       // Optional. Required if allowPartialPayment=true
  "thankYouMessage": "Thank you for your payment!"  // Optional. Max 200 chars
}

Success Response — 201 Created

{
  "success": true,
  "data": {
    "linkId": "lnk_a1b2c3d4e5f6",
    "linkUrl": "https://pay.rupeeflow.com/payment-link/lnk_a1b2c3d4e5f6",
    "expiryTime": "2026-03-23T10:30:00.000Z",
    "amount": 1500.00,
    "status": "pending"
  }
}

Validation Rules

FieldRule
amountRequired, > 0, max 2 decimal places, max ₹5,00,000 per link
emailRequired, valid RFC email format
mobileRequired, exactly 10 digits, must start with 6–9
expiresInMinutesRequired, > 0, max 43200 (30 days)
minimumAmountRequired if allowPartialPayment=true, > 0, < amount
thankYouMessageOptional, max 200 characters
descriptionOptional, max 500 characters

6. Payment Initiation APIs

ℹ️
Payment Gateway Integration These endpoints bridge the frontend checkout with the payment gateway (e.g., Razorpay, Cashfree, PayU, Juspay). The frontend sends payment details, the backend initiates with the gateway, and returns the required redirect / intent / session data.

6.1 Initiate Payment

POST /payment-links/:linkId/initiate

Initiates payment for a given payment link. Called when customer clicks "Pay Now" for any method.

Request Body

{
  "paymentMethod": "upi",          // Required: qr | upi | card | netbanking
  "amountToPay": 1500.00,         // Required: actual amount (may differ if partial)

  // ── UPI-specific fields ──────────────────────────────
  "upiId": "rahul@paytm",          // Required for method=upi
  "upiApp": "phonepe",             // Optional: phonepe | gpay | paytm | bhim | amazonpay | cred

  // ── Card-specific fields ─────────────────────────────
  "card": {
    "number": "4111111111111111",   // 16-digit card number
    "name": "Rahul Sharma",      // Cardholder name
    "expiry": "12/27",            // MM/YY
    "cvv": "***"                 // 3-4 digits (never log/store in plain text)
  },

  // ── Net Banking-specific fields ──────────────────────
  "bankCode": "HDFC"               // Required for method=netbanking
}

Success Response — 200 OK (UPI/QR)

{
  "success": true,
  "data": {
    "transactionId": "txn_xyz123",
    "status": "processing",
    "upiIntent": "upi://pay?pa=merchant@upi&pn=Acme&am=1500&tn=INV1042",
    "qrCodeUrl": "https://cdn.rupeeflow.com/qr/lnk_a1b2c3d4e5f6.png",
    "pollingIntervalMs": 3000   // Suggested interval for status polling
  }
}

Success Response — 200 OK (Card / Net Banking)

{
  "success": true,
  "data": {
    "transactionId": "txn_xyz123",
    "status": "processing",
    "redirectUrl": "https://bank.example.com/3ds?session=abc",
    "redirectMethod": "GET"   // GET or POST
  }
}
🔒
Security — Card Data Card details must NEVER be stored in plain text. Process card data through a PCI-DSS compliant gateway. Tokenize immediately on receipt. Consider using the gateway's JS SDK to directly tokenize on the frontend without card data ever reaching your servers.

8. Webhooks & Callbacks

ℹ️
Payment Gateway Callback The backend must expose a webhook endpoint for the payment gateway to POST the final payment result. This is how the status of a payment link gets updated from processing to success or failed.

8.1 Payment Gateway Webhook (Inbound)

POST /webhooks/payment-gateway

Received from payment gateway after payment completion.

🔒
Verify webhook signatures — validate HMAC-SHA256 signature from gateway before processing. Reject requests with invalid or missing signatures.

Expected Processing Steps

1
Verify signatureValidate HMAC or RSA signature in headers
↓
2
Extract linkId & txnRefIdFrom webhook payload
↓
3
Update PaymentLink statusSet to success/failed, store txnRefId, amountPaid, paidAt
↓
4
Send notificationsEmail/SMS confirmation to customer; alert to merchant
↓
5
Return 200 OKAcknowledge receipt to prevent retry by gateway

9. Encryption & Security

9.1 Payload Encryption (AES-256-GCM)

The frontend uses AES-256-GCM encryption for sensitive fields passed in URLs or session tokens. The backend must implement matching decryption.

Algorithm Details

PropertyValue
AlgorithmAES-256-GCM
Key Length256-bit (32 bytes)
IV Length12 bytes (random per encryption)
Auth Tag Length16 bytes
Output FormatBase64 encoded: iv(12) + authTag(16) + ciphertext
Key SourceShared secret: ENCRYPTION_KEY (32-char string)

Encryption / Decryption (Node.js)

// Decryption — matches frontend encryption.utils.ts
const crypto = require('crypto');

function decrypt(encryptedBase64, keyString) {
  const key = Buffer.from(keyString, 'utf8').slice(0, 32);
  const buffer = Buffer.from(encryptedBase64, 'base64');

  const iv       = buffer.slice(0, 12);
  const authTag  = buffer.slice(12, 28);
  const ciphertext = buffer.slice(28);

  const decipher = crypto.createDecipheriv('aes-256-gcm', key, iv);
  decipher.setAuthTag(authTag);

  const decrypted = Buffer.concat([
    decipher.update(ciphertext),
    decipher.final()
  ]);

  return decrypted.toString('utf8');
}

RequirementDetails

11. Complete Flow Walkthroughs

Flow A — Merchant Creates a Payment Link

1
Merchant opens dashboard Calls GET /payment-links?page=1&limit=10 to load existing links
↓
2
Merchant fills Create Link form Fields: amount, email, mobile, name, expiry, description, notifications, partial payment, thank you message
↓
3
Frontend submits Calls POST /payment-links with full payload
↓
4
Backend creates link Generates linkId, stores in DB, sends email/SMS if requested, returns { linkId, linkUrl, expiryTime }
↓
5
Frontend shows success modal Merchant copies/shares link. QR generated via GET /payment-links/:id/qr

Flow B — Customer Completes Payment (UPI)

1
Customer opens link GET /payment-link-details/{linkId} — check status, show checkout if pending
↓
2
Customer selects UPI tab Enters UPI ID and clicks Pay
↓
3
Frontend initiates payment POST /payment-links/{linkId}/initiate with { paymentMethod: "upi", upiId, amountToPay }
↓
4
Backend sends collect request to UPI gateway Marks link as processing, returns transactionId
↓
5
Frontend polls for status GET /payment-links/{linkId}/status every 3 seconds (up to 5 minutes)
↓
6
Gateway webhook received Backend updates link to success, stores txnRefId
↓
7
Polling gets success Frontend shows success screen with thank you message, txnRefId, merchant name

Flow C — Customer Completes Partial Payment

1
Link loaded Response has allowPartialPayment: true and minimumAmount: 500, total amount: 2000
↓
2
Customer selects "Pay Custom Amount" Frontend validates: 500 ≤ customAmount ≤ 2000
↓
3
Payment initiated with custom amount POST /payment-links/{linkId}/initiate with amountToPay: 800
↓
4
Backend records partial payment Status becomes success. Remaining balance 1200 should be tracked (TBD: create new link or mark partial)

12. Suggested Enhancements & Open Questions

Recommended Backend Features

#FeaturePriorityNotes
1Payment Link Short URLHighShorten /payment-link/{uuid} for cleaner WhatsApp sharing. Use a slug or nanoid.
2Bulk Link CreationMediumAllow uploading a CSV to create multiple links at once.
3Link TemplatesMediumSave link settings as reusable templates (e.g., "Monthly Invoice").
4Payment Retry SupportHighIf payment fails, allow customer to retry without a new link. Return a retry token.
5Multi-party Partial PaymentsLowTrack cumulative partial payments against a single link (group payment use case).
6Realtime Status via WebSocket / SSEMediumReplace polling with WebSocket push when payment status changes — better UX.
7Invoice PDF attachmentLowAttach a generated invoice PDF to the email notification sent on creation.
8Refund APIMediumMerchant-initiated refund for completed payments. POST /payment-links/:id/refund
9Embed / Widget TokenLowGenerate a signed token for embedding payment widget on external websites.
10Card Tokenization via Gateway SDKHighUse gateway-provided JS SDK to tokenize cards client-side. Never route raw card data through your servers.

Open Questions for Backend Team

  1. Which payment gateway will be integrated (Razorpay, Cashfree, Juspay, PayU)?
  2. Should GET /payment-links/:id be one unified endpoint for both merchant and customer, or two separate endpoints?
  3. What should happen after a partial payment — is the link marked done, or do we create a new link for the remaining balance?
  4. Are analytics events (opens, views) tracked by the backend, or should the frontend call a separate analytics service?
  5. What is the auto-reminder schedule — exactly 24h after creation, or relative to link expiry?
  6. Should the merchant be able to edit a pending payment link (change amount, expiry)?
  7. Is there a need for a guest checkout where the customer fills in their own name/email (for links without pre-filled customer info)?
  8. Should linkId be a UUID or a shorter, URL-friendly nanoid (e.g., lnk_Xk3mN9pQ)?
